# 提案手法の詳述：次回の執筆用

研究テーマ：VR遠隔協調作業(意味的空間音声・通信手法)のためのScene Tokenの構成

題目は固定。これは本文を書くための作業枠であり、提案仕様の確定や完成原稿ではない。
まず概要全体の材料を3,000～4,000字程度で書き、後から指定様式の2ページへ圧縮する。提案手法を全体の約半分とする。現在の保存済み短文本文は359文字（題目・見出し・空白・改行を除く）。書ける見込みと執筆済みの分量を区別する。

## 次回の最初の一作業

以下の1～6を、既存コードを根拠に文章へ展開する。最初は提案手法だけで1,500～2,000字程度を目安にする。字数のために未実装の仕様や利点を作らない。
成果物は「説明本文＋項目表＋構成図案＋未確定事項」。実装済み・設計案・要検証を明示する。

## 1. 再現する状況と必要な情報

書くこと：誰が、どの部品を、どこへ操作したか。現在の状態と変化の履歴を区別する。発話・工程・音響文脈のどこまでを今回の検討対象にするか。
注意：発話意図や指示と操作の対応は自動取得済みではない。

## 2. Scene Tokenの項目と関係

書くこと：識別子、時刻、イベント種別、主体、対象物、取付先、工程、音響文脈。必要性と欠落した場合の影響を項目表にする。
根拠：AssemblyObservation、CapturedAudioContext、SceneToken、RelationFrameの現行定義。
注意：取得観測の全項目が現在のsender-framesへ入るわけではない。観測形式・送信形式・最終提案を混同しない。

## 3. 生成・関連付け・更新

書くこと：SDK通知の取得、共通イベントID、同じプロセス内の時刻、音源ごとの文脈、初期スナップショット、追加生成された取付点への購読。
注意：端末間時刻同期と実操作成立tickの精度は未確認。

## 4. 送受信と受信側の復元

書くこと：実装済みの構造化メッセージ・簡易関係グラフ、参照と時刻、改訂、候補集合の完全性、受信側で問い合わせる事実。
注意：記録基盤と関係プローブの接続範囲を確認し、未実装の状態復元を実装済みと書かない。

## 5. 一つの具体例と不明値

人工的な説明例として、部品M1の把持→解放→取付を追う。各段階の観測と関係を表にする。
把持者が分かっても取付通知に主体がなければunknownとする。頭部姿勢と実音声、欠測と適用外、操作通知と初期状態を区別する。
この例は説明用であり、人間の実操作結果ではない。

## 6. 構成を選ぶ理由と対照

書くこと：どの情報がどの問い合わせに必要か、関係明示の負担は何か、構造化ログでも復元できる範囲はどこか。
比較には同一観測・同一事前知識を与える。関係の明示だけで新規性・精度向上を主張しない。追加観測の効果、表現の効果、処理の事前計算を分ける。

## 完了の目安

- 読者が構成図と具体例から、入力→生成→送受信→復元を追える。
- 各項目の採用理由と、不明・欠測の扱いを説明できる。
- 実装済みと設計案の境界、比較で確かめる問いを明示できる。
- 背景・目的とつながり、結果を先取りした表現がない。

その後、背景・目的、評価方法、現在の確認結果、考察、結論を加えた全体初稿を作る。実操作の取得・独立照合は研究室で並行して進める。
