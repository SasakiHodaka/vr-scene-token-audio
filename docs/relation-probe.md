# 意味関係の最小実装・予備評価

状態：研究仮説を探索的に検証する最小実装。Tokenの最終仕様や新規性の承認を意味しない。
従来の「仕様未承認のため実装を保留」という段階から、ユーザーの指示に基づき、仮説の修正を前提とした実装・測定へ進む。

## 仮説と検証範囲

仮説候補：関係の重要度だけで削減する場合に比べ、受信側の問い合わせに必要な参照・判定状態・時間対応も保持対象にすると、同じ通信量で意味的な再現誤りを減らせるか。

これは既存の情報削減原則の適用を調べる実証仮説で、新しい符号化・原子性・差分通信の提案ではない。
過去に棄却した「関係単位なら既存ログより優れる」という一般仮説を復活させない。
E1（送信側の導出結果の取得）は正確性の基準。真の発話意図・人間の作業効率・AI支援は対象外。

最初の測定では参照・時刻・判定状態を全方式で保護し、候補集合の部分削減と全体保持を比較する。
このため初期仮説の全要素を検証したことにはならない。参照欠落を意図的に作って優位性を演出しない。
一般的な整合性保護でも同じ効果が得られる場合はScene Token固有の利点としない。

## 実装

- `RelationObservationSource`：発話IDを入力し、Unityのpointer Transformと登録Colliderから全交差候補を導出。距離による順位付けや意図の確定は行わない。
- 観測不足と、判定済み空集合を区別。過去結果を位置変更で書き換えない。
- `ObserveOperation`：操作者・物体・操作・結果を既存の操作コールバックから渡す接続点。デモはボタン入力。ドローン組立側の自動取得は未接続。
- `RelationWire`：同じ意味を構造化メッセージまたは簡易的な関係グラフJSONで符号化。グラフ版は結果メタデータ＋値へのエッジであり、特定の既存Scene Graph実装の再現ではない。
- `RelationReceiver`：受信バイト列から状態を復元。セッション・発話・観測時点・改訂を区別し、旧版への巻き戻りと不完全な候補集合の公開を防ぐ。
- `RelationUdpEndpoint`：任意のUDP送受信。初期評価はJSONループバック、追加試験は同一PC内のUDP。再送・断片化・配送保証は未実装。

新規コードは`SceneTokenAudio.Research`に分離し、既存の8項目の音響Tokenを変更しない。
以前の確認用コピーにある音響制御分離の未コミット変更は本変更に混ぜない。

## 公平な比較条件

全方式に同じ入力・優先度・参照・判定状態・時刻・改訂・受信側規則を与える。
独立した[期待値](../Evaluation/relation-probe/expected.json)は評価器だけが読み、送信・復元APIには渡さない。
[入力](../Evaluation/relation-probe/input.json)は人工的なS4/S5の結果列。幾何導出の正しさは別のUnity Colliderテストで確認する。
最終形式は同じUTF-8 JSON。1更新あたり256/384/512/768/1024/2048 bytesの予算で比較。

| 方針 | 処理 |
|---|---|
| Full | 全結果を保持する無制限の基準。予算超過を明記し、制約内方式として比較しない |
| RankedItems | 入力優先度順で保持し、全候補が入らなければ入る候補だけ送る。受信側には元の候補数を伝え、不完全なら公開しない |
| GenericClosed | 同じ結果の候補集合を完全に送れる場合だけ保持する。一般的な整合性保護の対照 |
| TokenClosed | GenericClosedと意図的に同一の処理。名前による優位性がないことを確認する対照 |

RankedItemsはPark & Yoonの実装や学習した重要度の再現ではない。論文の頻度モデル・言語モデルによる冗長性判定を検証したとは扱わない。
一般的な閉包・整合性保護を提案側に独占させないため、GenericClosedを残す。
候補が部分欠落したら未復元として一致率を下げる。単一候補として公開して誤りを増やす弱い受信側は採用しない。

## 評価指標と再現手順

- 完全一致：6件の結果更新を対象に、ID・主体・発話・関係種別・観測時刻・改訂・判定状態・候補集合が独立した期待値と一致するか。欠落・旧版は不一致。
- 誤単一候補：正解が複数候補なのに受信側が単一候補を公開した件数。
- 判定状態混同：公開された結果のevaluated/insufficientが正解と異なる件数。未復元とは分ける。
- 通信量：全JSONエンベロープのUTF-8 bytes。通信プロトコルのヘッダーは含めない。共有辞書・外部履歴の利用はない。
- 処理時間：削減・符号化と、復号・復元のCPU時間を分ける。5更新分の合計。通信の更新遅延とは異なる。

同じ5フレームを各設定3回ウォームアップ後、20回反復する。2形式×4方針×6予算×20反復＝960行。
20回は同じ入力の処理時間反復であり、20件の独立シナリオではない。統計的な性能一般化をしない。

1. Unity 6000.0.58f2でプロジェクトを開く。
2. `Tools > Scene Token Research > Run Synthetic Relation Probe`で評価。出力は`Logs/relation-probe`。
3. または`Tools/Run-RelationProbe.ps1`で評価とデモシーン生成。
4. `python Tools/Summarize-RelationProbe.py`で生データ・要約・環境・入力／コードのハッシュを保存。
5. `Tools/Run-UnityTests.ps1`で既存回帰・候補欠落・順序逆転・旧結果訂正・幾何導出・UDPを確認。

デモ：`Tools > Scene Token Research > Create Local Relation Demo`、または生成済み`Assets/Scenes/RelationProbe.unity`を開いてPlay。
観測不足→複数候補→単一候補→物体移動をボタンで確認し、送信JSONと復元結果を表示する。これは指差し計測済みの人間実験ではない。

別受信端への接続：有効なGameObjectへ`RelationUdpEndpoint`を追加し、受信側のlistenPortと送信側のremoteHost/remotePortを設定。
送信側はlisten=falseとし、`RelationObservationSource.udpSender`へ割り当てる。受信側はReceiverから結果を取得できる。
ローカル確認用コピーは引き続き生成し、UDPにも同じJSONを送る。LAN別端末・Photon・Quest実機での検証は未実施。

## 初回結果の判断

Unity 6000.0.58f2のWindows Editor / batchmode / nographicsで、EditMode 33/33件、PlayMode 4/4件が成功。
既存音響テストを含み、追加のPlayMode試験で別受信コンポーネントへのlocalhost UDP送信・復元を確認した。
LAN・Quest実機・実音声・人間の指差し・ドローン組立の操作イベント接続は未検証。

測定データは[recorded](../Evaluation/relation-probe/recorded/)に保存。
測定した固定予算ではRankedItems、GenericClosed、TokenClosedの一致件数に差はなかった。
GenericClosedとTokenClosedは同じ処理のため、この一致を独立した二手法の比較証拠とはしない。
部分候補を受信側が公開しないことは、予算を1 byte刻みで探索する別のテストで確認。

| 条件 | 一致件数／更新数 | JSON総量 |
|---|---|---|
| 全保持・構造化メッセージ | 6/6 | 1536 bytes |
| 全保持・簡易関係グラフ | 6/6 | 1746 bytes |
| 構造化メッセージ・384 bytes/更新・削減3方針 | 5/6 | 1350 bytes |
| 構造化メッセージ・512 bytes/更新・削減3方針 | 6/6 | 1536 bytes |
| 関係グラフ・512 bytes/更新・削減3方針 | 5/6 | 1514 bytes |
| 関係グラフ・768 bytes/更新・削減3方針 | 6/6 | 1746 bytes |

誤単一候補・判定状態混同はこの入力と全測定条件で0件。ただし256 bytes/更新では全結果が未復元であり、0件を高品質の証拠にしない。
グラフ形式のバイト差は明示エッジ等の符号化オーバーヘッドで、Scene Graph一般の不利さやScene Tokenの新規性を意味しない。
現時点で仮説を支持する差は得られていない。これを完成した比較実験・新規性の実証とせず、動作する公平な測定基盤と限定的な予備結果として扱う。
