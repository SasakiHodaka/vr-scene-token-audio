# Scene Token研究方針

更新日：2026-11-06。これまでの研究軸を維持し、関連論文を仕様と評価の根拠として位置付ける。以下の仕様案・評価条件は11月8日までに具体化するもので、実験結果や新規性を確定した記述ではない。

## 研究テーマと目的

**研究テーマ：VR遠隔協調作業（意味的空間音声・通信手法）のためのScene Tokenの構成。**

VR遠隔協調作業に必要な音声・空間・動作・作業状況を統合的に表現するScene Tokenを構成し、作業場面ごとの要求条件に適した情報表現方法を明らかにする。
同じ作業記録から複数構成を生成し、必要情報の保持・作業状態の再現と、データ量・処理時間との関係を検証する。

研究の中心はScene Tokenそのものの構成。意味的空間音声・通信は応用先であり、既存の音響制御を実装資産として再利用する。
LLMの学習、Speech Tokenizerの開発、受信者選択、AIによる情報提示、緊急警告は現在の主要成果に追加しない。
特に11月15日まではTOEIC対策と並行し、新規モデル学習や複雑な音声処理を行わない。

## Scene Tokenの定義と仕様上の論点

Scene Tokenとは、VR空間における音声・環境・作業者の動作・作業状況を、AIやコンピュータが統合的に処理できるように構造化した情報表現単位である。
現段階では構造化レコードをTokenと呼ぶ設計であり、学習型の離散コードや連続埋め込みとは区別する。

仕様案として、共通の観測時刻における状態と、直前の更新区間に発生したイベントを分けて保持する。
1 Tokenの対象範囲、更新周期、イベント保持期間、座標系、欠測表現、時刻の基準・許容差は仕様確定時に明記する。
既存のアプリ起動後時刻は単一プロセスの観測に利用できるが、複数端末の時刻同期を実装済みとは扱わない。

| 情報 | 主な内容 | 明らかにしたいこと |
|---|---|---|
| 音声 | 発話内容、話者、発話時刻。意図・音声特徴は必要性に応じて検討 | 誰が何を伝えたか |
| 空間 | 位置・方向・距離・遮蔽・対象物 | どこで、どの対象に関して起きたか |
| 動作 | 移動、把持・解放・取付などの操作、操作者・対象物ID、イベント時刻 | 誰が何をしたか |
| 作業 | 工程、進行・完了状態、依存関係、時間制約 | どの作業状況で、次工程へ進めるか |

共通の時刻・作業者ID・対象物ID・工程IDで関連付ける。情報をJSONへ追加するだけでなく、保持する粒度と関係が作業上の問いに答えられるかを検証する。
まずは固定発話テキストや意味ラベルを入力し、実際の音声認識の誤りとは分けて表現方法を評価する。その場合、実音声処理を検証したとは主張しない。

## 研究質問と比較構成

- RQ1：各作業場面の状況を表現・再現するために、どの情報が必要か。
- RQ2：動作情報・作業情報の追加で、どの必須情報の保持・状態再現が改善するか。
- RQ3：その改善に対して、データ量と生成・更新時間はどれだけ増加するか。

| 構成 | 内容 | 主な検証対象 |
|---|---|---|
| C1 | 音声＋空間 | 発話と位置・対象関係 |
| C2 | C1＋動作 | 把持・取付などの操作状況 |
| C3 | C2＋作業状態 | 工程完了・前提条件・引き継ぎ |

C1〜C3は本実験の比較構成名。既存のBaseline／Always Clear／Adaptiveは音響制御方式であり、別の比較軸として扱う。
C3を最終解と決めず、場面ごとに必須情報を満たす構成とコストを比較する。削減案C4は比較結果が得られてから検討し、必須成果を増やさない。

## 要求条件の具体化

具体的な初期仕様・人工入力・独立した期待値は[3場面の要求条件・正解仕様 v0.1](scenario-spec.md)を参照。

ドローン組立の既存シーンを再利用し、まず以下の場面を候補にする。実際に取得できる操作イベントと工程管理に合わせて確定する。

| 場面 | Tokenから答えたい問い | 正解として準備する事実の例 |
|---|---|---|
| 部品の指示 | 誰が、どの部品について何を伝えたか | 発話ID、話者ID、発話内容、参照部品ID |
| 部品の把持・取付 | 誰がどの部品を操作し、現在どうなっているか | 操作者ID、部品ID、把持・取付イベントと時刻、取付先 |
| 次工程への引き継ぎ | 何が完了し、前提条件を満たしているか | 工程ID、完了状態、依存工程、必要なら担当者 |

「その部品」の参照を事前入力で与える場合と、視線・指差しなどから推定する場合を区別する。事前入力だけで曖昧発話を自動解決できたとは扱わない。
全場面共通の評価対象を定め、各構成が表現できない事実も欠落として記録する。加えて場面別の成績を示す。

## 評価の約束

同じ入力ログからC1〜C3を生成する。更新周期・数値精度・シリアライズ形式・実行環境を統一し、シナリオ長と試行条件を記録する。
正解はシナリオの期待事実・イベントとして事前に準備し、Tokenや復元結果から生成しない。
入力の検証用ログを利用する場合も、Token生成ロジックを正解判定に再利用せず、期待値との一致を確認する。

| 指標 | 定義・測定上の注意 |
|---|---|
| 必要情報保持率 | 事前定義した必須事実のうち、正しい値・許容誤差・許容時間差で取得できる割合。キーの存在だけで判定しない |
| 状態再現 | 全構成で同じ状態項目を復元し、独立した正解と比較。離散状態の一致と位置・時刻の誤差を分ける。未復元の割合も示す |
| データ量 | UTF-8等の固定形式で1 Tokenのバイト数と、同じシナリオ時間の総バイト数を測る。入力ログ・評価CSVのサイズとは区別 |
| 処理時間 | 生成・更新、シリアライズ、収集、I/Oを区別し、測定範囲を明記。中央値・95パーセンタイル等を示し、微小処理は反復計測する |
| 情報損失 | 保持率と同じ分母なら補数となる。独立した主要指標を増やさず、欠落事実・原因の分析に使う |

復元規則は実験前に固定する。工程ラベルをそのまま出力する一致率と、操作履歴から工程完了を復元する成績を混同しない。
Token生成の妥当性と、人間の理解・作業効率の改善は別の主張。今回の客観評価だけで後者まで結論しない。
デモ動画は動作証拠であり、構成の優位性は比較実験の数値で判断する。

関連付けそのものの効果を検証するなら、同一情報項目で関係参照の有無を比較する追加実験が必要。
これはC1〜C3を置き換える必須課題にはせず、行わない場合は主張を情報構成の比較に限定する。

## 文献の使い方と新規性の検討

文献リンク・詳細は[関連論文](related-papers.md)を参照。

| 文献 | 本研究での役割 |
|---|---|
| Workspace Awareness | 協調作業で保持すべき情報の要求条件を導く |
| Dynamic Scene Graphs／3DGraphLLM | 作業者・部品などの関係表現を検討し、既存表現との差を確認する |
| Point-3D LLM | 他条件を固定した構成比較と結果報告を参考にする |
| SceneReasoner | 要求に応じた情報選択・冗長情報の削減を検討する |
| SceneVerse | 発話中の対象と3D物体の対応付けを検討する |
| Moshi／VQ-VAE等 | 学習型Tokenとの違いを説明し、将来の接続方法を検討する |

既存モデルの導入を研究目的にしない。文献は、現在の軸である「作業場面ごとの必要情報・粒度・関係と、その保持／コスト」を根拠付けるために使う。
成果として目指すのは、VR協調作業の場面別要求からScene Token構成を導き、複数構成の比較と改良・再評価で適用範囲を示すこと。
独自性の確定には協調VR・工程表現・タスク依存の符号化の継続調査が必要であり、「4種類を統合した」「Tokenと命名した」だけを新規性にしない。
